## Concrete action-delivery failure

Reproduced directly through the real `SessionAuthority`: connect actor 0, submit sequence 1 with `fire: 'bolt', dash: true`, then sequence 2 with neutral input before calling `step()`. Both submissions return accepted; receipt becomes `{received:2, applied:2}`, yet `world.bolts.length === 0` and `actor.dashLeft === 0`. Existing bounded-intake/coalescing tests also cover the intended current behavior. This is not duplicated damage, but it makes a consumed high-water mark insufficient for reliable cast/dodge delivery. Reordering can produce the same user-visible loss. Retrying actions safely will need action identity, deduplication, explicit outcome/consumption semantics, bounded queues/expiry and recovery-generation rules; simply resending an input risks duplicate actions.

## Stack decision and proposed corrective work

- **Keep the current browser/simulation prototype.** It demonstrates centralized combat/terrain authority, bounded replication, prediction/interpolation and recovery while preserving solo behavior. No renderer/engine migration is authorized or justified by these results alone.
- **Hold M1 closure and production transport selection.** Loopback HTTP is a useful development adapter with no external service/account or operational hosting dependency in this test. It provides no LAN/NAT/relay/authentication deployment proof or production cost estimate. Choosing a production transport requires a defined target platform/hosting model and measurements of an improved action path; do not add services solely to disguise a reliability problem in the input model.
- **Proposed M1.P8: reliable discrete actions.** Separate coalescible motion from casts/dodges; bounded action identities and acknowledgments must survive loss/reordering without duplicate effects, while old recovery generations cannot replay actions. Define a brief before implementation.
- **Proposed M1.P9: common-target feasibility scene.** Introduce only enough actor/ownership/replication support for two players plus a common damageable target; preserve opponent/ally targeting explicitly and test both players' contributions. Team policy needs an explicit choice before dependent gameplay changes; full enemy/encounter design remains M2.
- **Proposed M1.P10: responsiveness and final re-review.** Agree acceptable active-motion correction/stall, discrete-action response and terrain/cold-join budgets with the user; exercise an integrated workload and a two-human shared-clock Heavenly Step playtest. Tune or compare transport/stack alternatives against that evidence. Include basic simulation/frame-time/memory/traffic profiling at the selected load. Re-review the original M1 exit criteria before declaring the milestone closed.

These are provisional corrective phases added to keep incomplete work visible; this review does not authorize implementing them. Do not start M2 or change campaign, persistence, art, death or world-ownership policy here.
